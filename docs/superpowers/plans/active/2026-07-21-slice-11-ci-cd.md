# Slice 11 CI/CD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Status:** Active — promoted from `drafts/` on 2026-07-22. Source design:
> `docs/superpowers/specs/2026-07-21-slice-11-ci-cd-design.md`.

**Goal:** Match Slice 11's roadmap done criteria — CI runs `go test`, `go vet`,
`gosec`, `govulncheck`, `trivy fs`, and `gitleaks` and blocks merge to `main`
on failure; CD builds and scans a container image and automatically deploys
it to the real staging environment via Terraform, using Azure OIDC (no
stored client secret).

**Architecture:** Two GitHub Actions workflows. `ci.yml` runs six parallel,
independent jobs (`test`, `gosec`, `govulncheck`, `trivy-fs`, `gitleaks`,
`terraform-check`) on every PR and push to `main`; branch protection requires
all six before merge. `cd.yml` triggers only on push to `main` (i.e., only
after branch protection already required CI to pass) and builds the image,
scans it, authenticates to Azure via OIDC, pushes to the existing ACR, and
runs Terraform against real staging behind a `plan`/`apply` safety valve
(`TF_APPLY_MODE` repository variable), then verifies the resulting Container
App revision is healthy via the Azure control plane.

**Tech Stack:** GitHub Actions, Go 1.26.5, `gosec` v2.28.0, `govulncheck`
(`golang.org/x/vuln`), Trivy (`aquasecurity/trivy-action`), Gitleaks
(`github.com/zricethezav/gitleaks/v8` CLI installed via `go install`), GitHub
Code Scanning (SARIF), `azure/login` (OIDC), Terraform `deploy/terraform/`
(existing, from Slice 10).

## Global Constraints

- Never commit a secret value, connection string, or access key to any
  workflow file, tfvars file, or plan/PR text (matches `AGENTS.md` and the
  existing `deploy/terraform/README.md` security rule).
- Pin every newly introduced third-party (non-`actions/*`, non-GitHub-owned)
  GitHub Action to a full commit SHA, not a mutable tag — `aquasecurity/trivy-action`
  had 75 tags force-pushed/hijacked in a March 2026 supply-chain incident
  (verified via web search during plan-writing). First-party actions already
  used by this repo (`actions/checkout@v5`, `actions/setup-go@v6`) keep their
  existing major-version-tag convention; do not change those.
- CD must never touch runtime secrets (`hook-hmac-secret`,
  `graph-client-secret`, `password-payload-encryption-key`) — those remain
  the Slice 10 Task 7 manual Key Vault injection process.
- Production `terraform apply`, daily scheduled scans, weekly OWASP ZAP DAST,
  and any new VNet-internal scanning infrastructure are explicitly out of
  scope for this plan (see the design spec's §3 Out of Scope / Follow-up).
- Run `go test ./...` and `go vet ./...` after every Go source change in this
  plan; run `terraform -chdir=deploy/terraform fmt -check -recursive` and
  `terraform -chdir=deploy/terraform validate` after every Terraform file
  change.

### Task 2: Report-Only Test Coverage Summary in the `test` Job

**Files:**
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: the `test` job as left by Task 1 (steps: checkout, `setup-go@v6`
  with `go-version: "1.26.5"`, `go test ./...`, `go vet ./...`).
- Produces: no new job name; `test` still reports as one status check named
  `test` (branch protection in Task 8 references this same name).

- [ ] **Step 1: Add `-coverprofile` to the existing test step and a summary step**

The current `test` job (after Task 1) in `.github/workflows/ci.yml`:

```yaml
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-go@v6
        with:
          go-version: "1.26.5"
      - run: go test ./...
      - run: go vet ./...
```

Replace it with:

```yaml
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-go@v6
        with:
          go-version: "1.26.5"
      - run: go test ./... -coverprofile=coverage.out
      - run: go vet ./...
      - name: Coverage summary
        if: always()
        run: |
          if [ -f coverage.out ]; then
            {
              echo '## Test coverage'
              echo '```'
              go tool cover -func=coverage.out
              echo '```'
            } >> "$GITHUB_STEP_SUMMARY"
          fi
```

This is report-only: no coverage threshold is enforced, so a low-coverage
package never fails the job (current coverage ranges ~40%–100% across
packages, verified locally with `go test ./... -cover` during plan-writing;
`internal/httpserver` is the lowest at 40%). `if: always()` ensures the
summary still renders even if `go vet` fails, so reviewers can see coverage
alongside a vet failure. `coverage.out` is already covered by the root
`.gitignore` (`/coverage.out`), so it is never accidentally committed.

- [ ] **Step 2: Verify locally**

Run: `go test ./... -coverprofile=coverage.out && go tool cover -func=coverage.out | tail -5`
Expected: the last lines show per-package coverage percentages and a `total:`
line; exit code 0.

Run: `rm coverage.out` afterward (it is gitignored, but keep the working tree
clean for the commit in Step 3).

### Task 3: `gosec` CI Job with SARIF Upload

**Files:**
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Produces: a new job named `gosec`, independent of `test` (no `needs:`),
  becomes one of the six required status checks wired in Task 8.

- [ ] **Step 1: Add the `gosec` job**

Add this as a new top-level entry under `jobs:` in `.github/workflows/ci.yml`,
alongside (not nested inside) the existing `test` job:

```yaml
  gosec:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-go@v6
        with:
          go-version: "1.26.5"
      - name: Install gosec
        run: go install github.com/securego/gosec/v2/cmd/gosec@v2.28.0
      - name: Run gosec
        id: gosec
        continue-on-error: true
        run: gosec -severity medium -fmt sarif -out gosec-results.sarif ./...
      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@c3d42c5d08633d8b33635fbd94b000a0e2585b3c # v3.31.4
        if: always()
        with:
          sarif_file: gosec-results.sarif
      - name: Fail if gosec found Medium/High issues
        if: steps.gosec.outcome == 'failure'
        run: exit 1
```

`security-events: write` is required for `upload-sarif` to write to the
repository's Code Scanning alerts. `-severity medium` limits gosec's
reported/failing findings to Medium and High (gosec has no "Critical"
level); `continue-on-error: true` on the `gosec` step lets the SARIF file
still get produced and uploaded even when gosec's own exit code is non-zero,
and the final step turns that captured outcome back into a real job failure
so branch protection still blocks the PR.

### Task 5: `trivy-fs` CI Job with SARIF Upload

**Files:**
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Produces: a new job named `trivy-fs`, independent of the others; one of
  the six required status checks wired in Task 8.

- [ ] **Step 1: Add the `trivy-fs` job**

```yaml
  trivy-fs:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
    steps:
      - uses: actions/checkout@v5
      - name: Run Trivy filesystem scan
        id: trivy
        continue-on-error: true
        uses: aquasecurity/trivy-action@ed142fd0673e97e23eac54620cfb913e5ce36c25 # v0.36.0
        with:
          scan-type: fs
          scan-ref: .
          format: sarif
          output: trivy-fs-results.sarif
          severity: CRITICAL,HIGH,MEDIUM
          limit-severities-for-sarif: true
          exit-code: "1"
      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@c3d42c5d08633d8b33635fbd94b000a0e2585b3c # v3.31.4
        if: always()
        with:
          sarif_file: trivy-fs-results.sarif
      - name: Fail if Trivy found CRITICAL/HIGH/MEDIUM issues
        if: steps.trivy.outcome == 'failure'
        run: exit 1
```

`aquasecurity/trivy-action` is pinned to a full commit SHA (not the mutable
`v0.36.0` tag) per the Global Constraints section — `aquasecurity/trivy-action`
specifically had 75 tags force-pushed/hijacked in a March 2026 supply-chain
incident. Same `continue-on-error` + captured-`outcome` pattern as Task 3, so
the SARIF file is always uploaded even when Trivy's own exit code is 1.

`severity: CRITICAL,HIGH,MEDIUM` (not just `CRITICAL,HIGH`) is a deliberate
decision made during plan execution (not the original design spec's
recommendation) to match Task 3's `gosec -severity medium` gate, so both
tools use the same effective bar and Code Scanning surfaces the same range
of severities from either tool.

**`limit-severities-for-sarif: true` is required and was added after a real
CI failure during implementation (2026-07-22):** without it, this action has
a documented bug/limitation
([aquasecurity/trivy-action#309](https://github.com/aquasecurity/trivy-action/issues/309))
where setting `format: sarif` silently drops the `severity` filter from the
*actual* `trivy` invocation entirely — confirmed live in this repository's
own Actions run, where the job log read `Building SARIF report with all
severities` followed by `Running Trivy with options: trivy fs .` (no
`--severity` flag at all), causing the `exit-code` gate to fire on
UNKNOWN/LOW findings the plan never intended to gate on (reproduced locally
with `trivy fs --exit-code 1 .`, which found 2 UNKNOWN-severity findings in
`go.mod` and thus behaves differently from the intended
`CRITICAL,HIGH,MEDIUM`-only gate). Setting `limit-severities-for-sarif: true`
makes the action actually honor `severity` for both the SARIF content and
the exit-code decision.

### Task 6: `gitleaks` CI Job with SARIF Upload

**Files:**
- Modify: `.github/workflows/ci.yml`

**Interfaces:**
- Produces: a new job named `gitleaks`, independent of the others; one of
  the six required status checks wired in Task 8.

- [ ] **Step 1: Add the `gitleaks` job**

**Revised during implementation (2026-07-22):** the original design used
`gitleaks/gitleaks-action`, but running it for real on this repository's
GitHub Actions revealed two fatal problems: (1) that action is a
closed-source, env-var-only wrapper with **no** `args`/`with:` input at all
(`##[warning]Unexpected input(s) 'args', valid inputs are ['']` in the live
run) — it cannot be configured with `--report-format`/`--report-path` as
this plan originally assumed; and (2) it hard-requires
`GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` to scan `pull_request` events
(`##[error]🛑 GITHUB_TOKEN is now required to scan pull requests`), and even
with that token it has no supported way to write a SARIF file at a path
`upload-sarif` can read. It is a PR-commenting/artifact-upload tool, not a
generic CLI-to-SARIF wrapper. Fixed by installing and running the real
`gitleaks` CLI directly via `go install`, the same pattern Task 3 already
uses for `gosec` — this preserves full control over `--report-format sarif
--report-path` exactly as originally intended, and was verified working
both locally and (see Task 8) in a real GitHub Actions run.

```yaml
  gitleaks:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
      - uses: actions/setup-go@v6
        with:
          go-version: "1.26.5"
      - name: Install gitleaks
        run: go install github.com/zricethezav/gitleaks/v8@v8.30.1
      - name: Run gitleaks
        id: gitleaks
        continue-on-error: true
        run: gitleaks detect --source . --report-format sarif --report-path gitleaks-results.sarif --exit-code 1
      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@c3d42c5d08633d8b33635fbd94b000a0e2585b3c # v3.31.4
        if: always()
        with:
          sarif_file: gitleaks-results.sarif
      - name: Fail if gitleaks found a secret
        if: steps.gitleaks.outcome == 'failure'
        run: exit 1
```

`fetch-depth: 0` on checkout is required so gitleaks can scan full commit
history, not just the merge commit (matches the local verification in
Step 2, which scanned all 192+ commits). The Go module path is
`github.com/zricethezav/gitleaks/v8` (the module's own declared path, not
the `github.com/gitleaks/gitleaks/v8` GitHub org/repo name — `go install`
with the org-name path fails with "module declares its path as
zricethezav/gitleaks/v8"; verified locally during this revision). gitleaks
has no severity levels — any detected pattern match fails the job
(`--report-format sarif`, `--report-path`, and `--exit-code` are real
gitleaks CLI flags, verified locally and matching Task 3's install-then-run
pattern rather than a vendor GitHub Action).

  is untouched — a separate workflow file with a `paths:` trigger filter
  would never produce this status check on unrelated PRs, which would make
  Task 8's branch protection block those PRs forever waiting for a check
  that will never run.

- [ ] **Step 1: Add the `terraform-check` job**

```yaml
  terraform-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - name: Detect Terraform changes
        id: filter
        uses: dorny/paths-filter@7b450fff21473bca461d4b92ce414b9d0420d706 # v4.0.2
        with:
          filters: |
            terraform:
              - 'deploy/terraform/**'
      - name: Setup Terraform
        if: steps.filter.outputs.terraform == 'true'
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.9.0"
          terraform_wrapper: false
      - name: terraform fmt -check
        if: steps.filter.outputs.terraform == 'true'
        working-directory: deploy/terraform
        run: terraform fmt -check -recursive
      - name: terraform init (no backend)
        if: steps.filter.outputs.terraform == 'true'
        working-directory: deploy/terraform
        run: terraform init -backend=false
      - name: terraform validate
        if: steps.filter.outputs.terraform == 'true'
        working-directory: deploy/terraform
        run: terraform validate
      - name: No Terraform changes
        if: steps.filter.outputs.terraform != 'true'
        run: echo "deploy/terraform/** unchanged; skipping Terraform checks."
```

`dorny/paths-filter` is pinned to a full commit SHA per the Global
Constraints section (a single-maintainer action, lower scrutiny than a
large-org action, so treated the same as the newly introduced security-tool
actions). `hashicorp/setup-terraform@v3` is HashiCorp's own first-party
action; kept on a major-version tag consistent with how this repo already
treats `actions/checkout`/`actions/setup-go`. Every step after the filter
step is individually gated by `if: steps.filter.outputs.terraform == 'true'`
so the job as a whole always completes (and reports a pass) regardless of
whether Terraform changed — only the final "No Terraform changes" step runs
in the un-changed case. `terraform_wrapper: false` avoids the action's output
wrapper adding noise unrelated to `fmt -check`/`validate` exit codes.

`deploy/terraform/main.tf`'s `required_version` constraint before finalizing
this step — read the actual constraint from `deploy/terraform/main.tf` (it
was `>= 1.8.0` as of the Slice 10 design spec) and adjust the pinned version
here if that file has since changed.
